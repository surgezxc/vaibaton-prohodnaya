## Область и вывод

Посмотрены API, интерфейсы проходной, телефона, администратора и руководителя, авторизация, база и миграции, сервис лиц, помощник и провайдеры, Docker, тесты и документация. `alison` рассматривался как архив, а не действующий путь запуска.

Это работающий хакатонный MVP: телефон подтверждает попытку, сервер сравнивает лицо, открывает или закрывает смену, ведёт журнал и строит аналитику. Основа подходит для кейса; переписывать архитектуру целиком не требуется. Основные проблемы проверенной версии — защита факторов прохода, достоверность ответов помощника и переходы состояния.

Приоритеты:

- **P1:** исправить перед заявлением о выполнении ключевых требований; для инфраструктуры — блокер соответствующего сценария демонстрации.
- **P2:** ошибки и ограничения, влияющие на работу.
- **P3:** упрощение и сопровождение.

Ниже отдельно указано, что воспроизведено, что установлено чтением кода и где оценка зависит от выбранной семантики продукта. Успешные тесты не означают отсутствие перечисленных проблем.

## Замечания

### R01 — [P1] Сохранённое изображение проходит проверку «живого лица»

**Основание: воспроизведено с настоящим face-сервисом и весами; путь передачи изображения проверен по коду.**

Сервис оценивает один присланный кадр без подтверждения, что он снят сейчас для конкретной попытки. Один сохранённый кадр дважды получил `match=true`, `live=true`, score около `0.8770982`. На проходной есть штатная загрузка файла. При подтверждённой попытке это позволяет предъявлять старый кадр человека вместо его текущего присутствия. Проверка телефона и авторизация проходной для такого сценария всё ещё нужны; face сам по себе не выдаёт разрешение.

**Исправление:** проверяемая сервером последовательность кадров с заданием для текущей попытки. Удаление кнопки загрузки само по себе API не защищает; проверка хеша файла не защищает от изменения или перекодирования изображения. Без решения нельзя считать `live=true` доказательством присутствия человека сейчас. Атака с физической распечаткой или экраном не проверялась.

Источники: [сравнение лица](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/deliverables/a-shorokhov-face-model/services/face/face.py#L119-L129), [загрузка кадра](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/app/gate/page.tsx#L140-L149), [передача кадра в face](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/decide.ts#L193-L195).

### R02 — [P1] Access token позволяет заменить привязанный телефон

**Основание: воспроизведено на изолированном API и PostgreSQL.**

`POST /devices` принимает новый публичный ключ, отзывает старый и не требует подтверждения старым устройством или администратора. В проверке другой ключ зарегистрировался с ответом `201`, затем успешно подтвердил QR; прежняя привязка была отозвана. Фактор владения телефоном можно заменить, имея только токен учётки. Это не устраняет отдельную проверку лица, но ослабляет независимость факторов.

**Исправление:** отдельный процесс смены устройства — подпись старым ключом либо контролируемое восстановление через администратора. Первичную регистрацию также нужно отделить от последующей замены. Без этого компрометация токена позволяет перехватить привязку и отключить законный телефон.

Дополнительно воспроизведено: после отзыва устройства уже подтверждённая им попытка получает `allow`; актуальность `device_id` в `decide` не проверяется. Если отзыв должен немедленно прекращать возможность прохода, его нужно учитывать при окончательном решении, включая ожидающие попытки.

Источники: [регистрация устройства](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/devices.ts#L49-L65), [проверка подтверждения](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/decide.ts#L144-L147).

### R03 — [P1] Защита помощника от выдуманных фактов проверяет числа, но не смысл

**Основание: воспроизведено вызовами действующего `renderModelText`.**

Модель может поменять местами `{people}` и `{shifts}`, и результат пройдёт проверку. При фактах «3 человека, 9 смен» принят текст «Людей 9, смен 3». Также принято дополнительное утверждение «Ещё 3 человека эвакуированы», поскольку число `3` разрешено. Отсутствие новых чисел не гарантирует отсутствие новых фактов или правильную связь между полями и подписями.

**Исправление:** сервер формирует фактические утверждения из фиксированной схемы; модель выбирает допустимую формулировку, а не произвольные связи между словами и полями. Без этого ответы могут противоречить БД даже при `model_status=ok`.

Источник: [подстановка и проверка ответа модели](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/assistant.ts#L247-L300).

### R04 — [P1 для телефонов, исторический пункт] Compose требовал дополнительной настройки адресов и HTTPS

**Основание: конфигурация проверенной версии. Последующие изменения см. в таблице выше.**

В `ac95787` зашиты `localhost` для Keycloak и issuer; браузерные адреса по умолчанию используют HTTP. На телефоне `localhost` указывает на сам телефон. HTTPS только перед web оставляет проблемы с HTTP API, входом и mixed content. Замены двух `NEXT_PUBLIC_*` недостаточно: нужны согласованные issuer, hostname и разрешённые redirect URI.

**Исправление:** единый доступный телефонам HTTPS-адрес с маршрутами для web/API/Keycloak и проверка на физических устройствах. В последующих коммитах такой путь добавлен. Полный запуск новой конфигурации автором этого ревью не проверялся; исходное замечание не является утверждением о неисправности нового HTTPS-стенда.

Источник исходного замечания: [конфигурация `ac95787`](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/docker-compose.yml#L22-L80). Последующее решение: [Compose `9ee845b`](https://github.com/surgezxc/vaibaton-prohodnaya/blob/9ee845b/docker-compose.yml), [Caddy](https://github.com/surgezxc/vaibaton-prohodnaya/blob/9ee845b/infra/caddy/Caddyfile).

### R05 — [P2] Попытка может завершиться разрешением после истечения TTL

**Основание: воспроизведено на PostgreSQL с управляемой задержкой ответа face.**

Срок проверяется один раз перед обращением к сервису лиц. В PostgreSQL `now()` фиксируется на начало транзакции. В проверке срок попытки истёк во время ожидания face, но ответом стал `allow`. Ожидание блокировки также увеличивает промежуток между началом транзакции и решением.

**Исправление:** если TTL ограничивает момент разрешения, проверять текущее время после получения блокировки и повторно перед записью результата, используя `clock_timestamp()`. Если запрос, принятый до TTL, намеренно может завершиться позже, эту семантику нужно явно закрепить. Иначе фактический срок действия расходится с показанным пользователю.

Источники: [проверка TTL](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/decide.ts#L78-L85), [вызов face](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/decide.ts#L193-L195), [фиксация решения](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/decide.ts#L271-L278).

### R06 — [P2] Одновременные запросы создают два действующих QR одной проходной

**Основание: воспроизведено двумя параллельными запросами на изолированной базе.**

Замена устроена как `UPDATE` прежних попыток, затем `INSERT`. Когда действующей строки ещё нет, оба запроса могут пройти одновременно. Получены две активные попытки для одного `gate_sub`. Создание нового QR не всегда аннулирует предыдущий.

**Исправление:** сериализовать создание по проходной и закрепить правило частичным уникальным индексом для активных состояний, с обработкой конфликта. Без этого сохраняются несколько независимо действующих кодов, например при двух вкладках или одновременных запросах.

Источник: [создание попытки](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/attempts.ts#L58-L84).

### R07 — [P2] Дата пропуска сдвигается на день в московской временной зоне

**Основание: воспроизведено с `TZ=Europe/Moscow`.**

SQL `DATE` превращается в JavaScript `Date`, затем форматируется через UTC. Сохранённое `2027-12-31` вернулось как `2027-12-30`, хотя значение в БД оставалось `2027-12-31`. После открытия карточки и сохранения неправильная дата может попасть обратно в БД.

**Исправление:** передавать календарную дату строкой, без преобразования в момент времени, например через текстовое представление SQL или parser типа `DATE`. Без этого интерфейс показывает неправильную дату, а повторное редактирование способно изменять данные.

Источник: [сериализация даты](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/people.ts#L72-L75).

### R08 — [P2] API принимает токены без проверки назначения и типа

**Основание: воспроизведено на локальном RSA/JWKS с тестовым issuer.**

Проверяется issuer, но отсутствуют ожидаемый audience и проверка вида access token. Подписанный ID token с audience другого клиента и ролью `admin` принят как удостоверение администратора API. Подпись настоящая для тестового issuer: проблема в принятии неподходящего вида удостоверения, а не обходе криптографической проверки или самостоятельном повышении роли.

**Исправление:** настроить audience API в Keycloak и проверять его вместе с видом токена. Без этого токены того же issuer, выпущенные для другого назначения, могут использоваться в API при наличии нужных role claims.

Источник: [JWT-проверка](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/auth.ts#L44-L49).

### R09 — [P2] Ночные смены дают несогласованные отчёты

**Основание: воспроизведено на данных изолированной базы.**

Отчёт выбирает смены по дате начала, маршруты и посещения — по времени событий. Для смены с 23:00 предыдущего дня до 02:00 текущего, с посещением зоны в 01:00, heatmap и маршрут за текущий день показали данные, а отчёт показал ноль смен.

**Исправление:** определить единую семантику периода. Для отчёта о работе внутри периода выбирать пересекающиеся интервалы и считать время в его границах. Если отчёт именно о начавшихся сменах, явно подписать это и согласовать остальные показатели. Без этого одинаковый период на соседних экранах означает разные выборки.

Источник: [фильтрация смен](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/analytics.ts#L222-L226).

### R10 — [P2] Вопрос «за неделю» о зонах обрабатывается как вопрос об одном дне

**Основание: воспроизведено через маршрут помощника на изолированных данных.**

Парсер создаёт недельный диапазон, но функции зон и «меньше четырёх часов» получают только `period.from`. При существующих посещениях внутри недели ответом стало «Данных нет», поскольку SQL проверял только первый день диапазона.

**Исправление:** передавать обе границы периода в SQL либо прямо сообщать, что инструмент поддерживает только день. Без этого ответ выглядит корректным, но фактически относится к другому периоду.

Источники: [выбор периода](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/assistant.ts#L51-L59), [использование периода](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/assistant.ts#L371-L383).

### R11 — [P2] Ответ сохранения может присвоить новой карточке ID другого человека

**Основание: прослежен переход состояния по коду; отдельное браузерное воспроизведение не выполнялось.**

Пока сохраняется человек A, можно нажать «Новая карточка» и начать ввод B. Когда ответ для A приходит, `setDraft(current => …)` добавляет ID A в текущие поля B. Следующее сохранение обновит A данными B. Во время запроса заблокирована кнопка сохранения, но не смена карточки и не поля.

**Исправление:** блокировать смену карточки на время сохранения либо применять ответ только к той версии формы, которая отправила запрос. Без этого медленный ответ может привести к записи данных не того человека.

Источник: [обработка сохранения](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/app/admin/page.tsx#L146-L160).

### R12 — [P2] У администратора и руководителя нет полноценного жизненного цикла сессии

**Основание: чтение реализации сессии и сравнение с действующим PKCE-процессом.**

Password grant этих экранов сохраняет только access token; refresh token отбрасывается, срок при загрузке не проверяется. После истечения токена интерфейс продолжает считать пользователя вошедшим, а API возвращает `401`. Выход также обслуживает другую систему состояния, чем Keycloak `AuthProvider`.

**Исправление:** перевести эти экраны на уже используемый PKCE-процесс с обновлением токена и единым выходом. Без этого нужны ручной повторный вход и отдельная обработка рассогласованного состояния сессий.

Источники: [отдельная сессия](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/lib/session.ts#L71-L97), [существующее обновление токена](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/components/auth-provider.tsx#L43-L48).

### R13 — [P2, исторический пункт] Инструкция по привязке ссылается на отсутствующий элемент интерфейса

**Основание: чтение UI и требований API. Последующее исправление для `worker` см. выше.**

В проверенной версии админка требует `Keycloak sub` и сообщает, что он виден на телефоне после входа. Телефон показывает имя учётки, но не `sub`. Стандартный путь заведения нового рабочего требует доступа к Keycloak или инструментам разработчика.

**Исправление:** показать идентификатор с копированием либо дать администратору поиск учётки. В последующих коммитах добавлены endpoint и кнопка для конкретной учётки `worker`, а неверная подсказка убрана. Это решает исходную проблему для демонстрационного пользователя; общий выбор разных рабочих остаётся отдельным расширением.

Источники исходного замечания: [подсказка админки](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/app/admin/page.tsx#L193), [отображение учётки](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/components/auth-provider.tsx#L76-L88). Последующее решение: [directory](https://github.com/surgezxc/vaibaton-prohodnaya/blob/9ee845b/apps/api/src/modules/directory.ts).

### R14 — [P2] Корректная калибровка небольшого участка отклоняется

**Основание: воспроизведено вызовами функций геометрии.**

Определитель GPS-координат сравнивается с абсолютным порогом `1e-8` в градусах. Для трёх разных, не лежащих на одной прямой точек с разницей координат `0.00005` получены `calibrationUsable=false` и проекция `null`. Небольшой участок отвергается даже при корректной геометрии.

**Исправление:** центрировать и нормировать координаты, проверять вырожденность относительным критерием. Без этого валидная калибровка компактной зоны не сохраняется или не используется.

Источник: [порог калибровки](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/geo.ts#L54-L73).

### R15 — [P2] При ошибке сети руководитель видит «Сейчас внутри: 0»

**Основание: чтение обработки ошибки и рендера заголовка.**

Ошибка заменяет список на `[]`, а заголовок выводит его длину. Сообщение об ошибке присутствует, но одновременно показывается конкретное неверное число.

**Исправление:** состояние «данные недоступны» либо последний успешный список с временем получения. Без этого отсутствие ответа выглядит как отсутствие людей.

Источник: [обработка ошибки и заголовок](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/app/manager/page.tsx#L56-L86).

### R16 — [P2] Старые записи журнала нельзя последовательно просмотреть

**Основание: чтение UI и API выборки.**

UI запрашивает последние 100 записей. API ограничивает выборку максимумом 500 и не предоставляет пагинацию. Записи сохраняются в БД, но историю за пределами лимита нельзя последовательно просмотреть; фильтры по человеку или решению не заменяют пагинацию.

**Исправление:** пагинация по паре `at/id` и кнопка загрузки следующих записей. Без этого расследование старых событий требует прямого доступа к БД. Простое увеличение лимита лишь откладывает проблему.

Источник: [выборка журнала](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/journal.ts#L47-L74).

### R17 — [P2] Изображение плана не передаётся между пользователями и устройствами

**Основание: чтение механизма хранения; ограничение прямо отмечено в коде.**

Геометрия хранится на сервере, картинка — только в `localStorage` браузера администратора. Руководитель на другом компьютере получает зоны без загруженного фона. Для демонстрации в одном браузере это допустимое упрощение; для общей работы ролей оно мешает использованию плана.

**Исправление:** хранить изображение плана на сервере, связывая его версию с калибровкой и полигонами. Без этого фон нужно переносить отдельно, а геометрия и изображение могут расходиться.

Источник: [хранение изображения](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/lib/site.ts#L32-L45).

### R18 — [P2] Без модели ответ об отказах теряет причины

**Основание: чтение SQL, резервного ответа и интерфейса помощника.**

SQL собирает причины и количества, но резервный текст возвращает только «Отказов N». Интерфейс помощника не раскрывает полученные строки фактов. Вопрос «какие отказы» становится малоинформативным при недоступности провайдера, хотя нужные данные есть в БД.

**Исправление:** показывать причины и количества непосредственно из фактов независимо от генерации текста. Без этого полезность уже рассчитанных данных зависит от доступности модели.

Источники: [факты об отказах](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/assistant.ts#L138-L154), [резервный ответ](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/api/src/modules/assistant.ts#L241-L243), [интерфейс помощника](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/components/manager-assistant.tsx).

### R19 — [P3] Остались неиспользуемые реализации важных компонентов

**Основание: поиск потребителей по исходникам репозитория.**

У `device-key.ts`, `pass-code.ts`, `frame-camera.tsx` и `qr-scanner.tsx` не найдены потребители; вместе это 332 строки. Например, старая реализация ключа экспортирует его в `localStorage`, хотя активный сценарий использует другой механизм. Сейчас это не уязвимость действующего сценария, но источник путаницы и риска случайно подключить устаревшую реализацию.

**Исправление:** после подтверждения отсутствия потребителей удалить эти файлы. Без этого остаются конкурирующие примеры реализации критических функций. Измеримое упрощение — 332 строки; удаление зависимостей этим не подтверждено. В рамках ревью файлы не удалялись.

Источники: [device-key](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/lib/device-key.ts), [pass-code](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/lib/pass-code.ts), [frame-camera](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/components/frame-camera.tsx), [qr-scanner](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/apps/web/src/components/qr-scanner.tsx).

## Спорные решения и сопровождение

### Привязка к браузеру и физическое присутствие

Неэкспортируемый `CryptoKey` полезен, но не является доказательством аппаратной привязки к конкретному телефону. QR с TTL также допускает передачу изображения другому человеку внутри срока действия. Для демонстрационного сценария это может быть допустимо; обещание физического присутствия требует дополнительных механизмов. Эти ограничения отличаются от возможности заменить ключ по одному токену, описанной в R02.

### Калибровка face не заменяет независимую оценку

В сохранённом отчёте — 41 успешное сравнение своего человека из 52, 11 отказов своему и ноль ошибочных допусков на 468 чужих парах. Максимальный чужой score `0.686268` близок к порогу `0.69`. Это результаты калибровочного набора, а не независимая оценка. Нужна отдельная проверка новых кадров; снижать порог ради уменьшения отказов без неё рискованно. Полный набор сравнений для этого отчёта автор ревью заново не прогонял.

Источник: [сохранённый отчёт калибровки](https://github.com/surgezxc/vaibaton-prohodnaya/blob/ac95787/deliverables/a-shorokhov-face-model/reports/package-calibration.json#L1-L19).

### Две реализации помощника

Есть отдельный пакет помощника в `deliverables` и действующая реализация API. Успешные тесты отдельного пакета не подтверждают защиту активного маршрута `assistant`. Нужен один источник поведения и согласованный контракт фактов; механическое копирование пакета без согласования полей не является готовым исправлением R03.

### Документация

Документация местами отстаёт от кода. Например, корневой `AGENTS.md` сообщает, что продукта нет, хотя приложения существуют. Инструкции запуска и описания интеграций стоит сверить с текущим Compose. Это затрудняет подключение нового участника. Два коммита после проверенной версии уже обновляют часть инструкций; считать прежние замечания к запуску неизменными нельзя.

### Автоматические проверки

В проверенной версии не найдены GitHub Actions workflows, запускающие имеющиеся тесты. Для дальнейшей работы перечисленные воспроизведённые ошибки желательно закрыть регрессионными проверками и запускать их автоматически. Отсутствие CI здесь — рекомендация по сопровождению, а не выдуманное условие допуска к хакатону.

## Рекомендуемый порядок исправлений

1. Обеспечить свежесть кадра и защищённую смену привязанного устройства: R01, R02.
2. Ограничить модель допустимыми фактическими утверждениями: R03.
3. Подтвердить новый HTTPS-путь на физических телефонах; R04 уже затронут последующими изменениями.
4. Закрыть гонку QR, определить семантику TTL и исправить календарные даты: R05–R07.
5. Исправить назначение токенов, семантику периода и гонку сохранения карточки: R08–R11.
6. Доработать сессии, план, журнал и отображение ошибок; убрать подтверждённо неиспользуемые реализации.

**Вердикт для проверенной версии:** основа подходит для хакатона, но утверждение «нельзя пройти за другого» недостаточно защищено, пока остаются повторное предъявление кадра и замена телефона по одному токену. Вывод о текущем `main` требует учёта статусов последующих изменений и повторной проверки исправленных сценариев.
