# План по кейсу «Проходная»

Источник: кейс-docx + папка `Первый пакет` в [репо](https://github.com/surgezxc/vaibaton-prohodnaya). Ниже — только то, что в этих файлах. GPS, карта и треки в пакете **не найдены**.

Не берём бонусы из 7.2, пока не закрыт обязательный объём (кейс: баллов не дают, если обязательное не закрыто; сверх списка не штрафуют, но и не копят). Сценарии С1–С22 в docx не расписаны — не выдумываем.

Легенда статуса: **кейс** = обязательно; **выбор команды** = бриф сам отдаёт нам; **блокер** = нет данных.

## Обязательный объём (§4)

| № | Из кейса | Статус |
| --- | --- | --- |
| 1 | Проходная: вход и выход, снять лицо, получить подтверждение с телефона, результат и причина отказа | **кейс** |
| 2 | Телефон: средство подтверждения один раз; предъявлять на проходной; геолокация пока смена открыта | **кейс**; форма — QR (выбор команды 10.10). Статичный QR кейс снимает (§7.4) — только одноразовый QR на попытку |
| 3 | Сервер: подлинность прохода, нельзя за другого, смены, история перемещений, журнал попыток | **кейс** |
| 4 | Админка: заведение/правка с проверкой эталона, список со состоянием, журнал | **кейс** |
| 5 | Кто сейчас внутри и с какого времени | **кейс** |
| 6 | Аналитика: чаще / вовсе нет, маршруты, отчёт по смене и по человеку за период | **кейс**; детали в §4.1 |
| 7 | Помощник: вопросы обычным языком и сводки за период по данным системы | **кейс**; детали в §4.2 |

## Поток из §3 (без добавок)

1. **3.1 Заведение.** Данные человека + материал лица. Эталон не сохранить, если на фото нет человека или несколько людей. Рабочий получает на телефон средство подтверждения; свойство: нельзя переслать, скопировать, сфотографировать и использовать позже. Реализацию кейс не задаёт.
2. **3.2 Вход.** Контролёр инициирует. Сервер одновременно: подтверждение настоящее, актуальное, этого человека **и** перед камерой он (сравнение с эталоном, не «есть лицо»). Успех → начало смены, человек на объекте. Отказ → человеческая причина, запись в журнал.
3. **3.3 Смена.** Пока открыта — местоположение копится. Частота — выбор команды (видно на защите + батарея). Точки привязаны к этой смене; после закрытия в неё не пишутся.
4. **3.4 Выход.** Тот же механизм, что вход. Конец смены, отработанное время, больше не «на объекте».
5. **3.5.** Админ: список + журнал всех попыток. Руководитель: обстановка, аналитика, вопросы текстом. **Два разных UI** (выбор команды 10.10). Не склеивать.

## Аналитика §4.1

Отдельный раздел UI руководителя. Обязательно:

- схема площадки с зонами; способ нарезки — выбор команды, один, в документации, одинаковый для всех отчётов;
- привязка реальных координат к зонам — выбор команды, **задаётся через интерфейс, не правкой кода**;
- посещаемость за период: интенсивность; **пусто и мало визуально разные**;
- маршруты выбранных людей, люди различимы, есть подпись кто есть кто;
- фильтры на оба вида: день, диапазон дней, часы внутри дня, люди (один / несколько / все);
- одна метрика на всё (посещения / точки / время в зоне) — выбор команды, в доке и на защите одно и то же.

План-схема строится **по изображениям из пакета** (конец §5.3). В пакете три кадра камер, не генплан и не координаты:

- `Объект/Бетономешалка` — CAM-02A БЕТОН
- `Объект/Котлован` — CAM-05B КОТЛОВАН
- `Объект/Место для курения` — CAM-04A КУРИЛКА

Три имени зон берём из папок пакета. Как из трёх фото собрать схему и как в UI привязать GPS — выбор команды, в пакете привязки нет.

## Помощник §4.2

Должен отвечать на типы: кто сейчас на объекте; кто вчера < 4 часов; в какой зоне вчера больше всего людей; были ли отказы за неделю и почему. Сводка за период: сколько людей, сколько смен, отклонения, отказы, аномалии. Нет данных → явно сказать. Цифры считает система, модель формулирует.

## Каркас, который кейс требует, а стек — нет (§5)

| Пункт | Требование | Стек |
| --- | --- | --- |

| 5.2 | Свой UI у каждой роли; не swagger и не админка из коробки; весь сценарий роли через UI; живые данные сервера; состояние по-русски; UI под телефон / планшет / ПК | фреймворк — выбор команды |

| 5.5 | Отдельными файлами: запуск; схема; журнал решений 3–6; переход на локальную модель; ограничения; отчёт об ИИ | частично есть architecture + decisions |
| 5.6 | Каждый объясняет свой код; правка 10–15 мин на защите; судья заводит своего человека (Д9) и чужие фото/маршруты | не зашивать демо-фиксатуры как единственный путь |

## Не делаем, потому что кейс так сказал (§6)

Натив. Свой train распознавания. Реальная стройка (имитация гео — да, способ показать судьям). Промышленный failover. Интеграции с учётом. Дизайн ради дизайна. Бонусы до закрытия §4.

## Допуск, без которого баллы не считают (§7.1)

Д1 стенд по инструкции · Д2 бэкенд решает проход · Д3 три фронта (проходная, телефон, админ) · Д4 персист · Д5 модель реально вызывается и результат используется · Д6 слой + два провайдера + инструкция · Д7 git · Д8 доки 5.5 · Д9 проход человека судей · Д10 нельзя за другого · Д11 владение кодом.

Снятие (§7.4) совпадает с запретами выше: клиент решает; «есть лицо»; статичный токен; память/файл; рисованная аналитика; выдуманные цифры; нет модели / заготовленный ответ; секреты; «не смотрел код».

## Порядок работ (только обязательное)

1. Репо, .env.example, gitignore, черновики доков 5.5 (уже начато).
2. Сервер + хранилище + журнал (5.1, Д2, Д4).
3. Заведение человека и отбраковка эталона 0 / 2+ лиц (3.1, объём 4).
4. Телефон: сканирует одноразовый QR **с планшета** (контролёр открыл попытку). Закрыл QR — отмена; открыл снова — новый код.
5. Проходная вход/выход: кадр + подтверждение, решение на сервере, человеческий отказ (3.2, 3.4, объём 1, Д9, Д10).
6. Смена + гео раз в **60 секунд** (выбор 10.10), точки только в открытую смену.
7. UI руководителя: зоны Бетон / Котлован / Курилка из пакета; метрика — **посещения**; пусто = 0 заходов, мало ≠ пусто; маршруты; фильтры. Границы зон **рисуются в админке** на схеме из трёх фото (выбор 10.10), не в коде.
8. Помощник: внешний **GigaChat**; локальный второй обязателен (§5.3).
9. Имитация гео: на телефоне кнопки «Бетон / Котлован / Курилка» (выбор 10.10). Способ показать судьям.
10. Доки 5.5; 15 коммитов от всех. Разделение ролей — позже.

## Решения команды (10.10)

- Вход и роли — **Keycloak** (организаторы: его используют). Passkey нет.
- Админ и руководитель — **разные** интерфейсы.
- Подтверждение на телефоне — **QR**. По кейсу (§3.1 и снятие §7.4) это не может быть одна и та же картинка навсегда: QR одноразовый на попытку, фото старого QR — отказ.
- Гео: **раз в минуту**, пока смена открыта.
- Внешняя модель: **GigaChat**. Локальный провайдер всё равно обязателен.
- Кто какой кусок кода пишет — решите позже (Д11 всё равно потребует, чтобы каждый знал свой файл).
- Метрика зон: посещения.
- Имитация движения: кнопки Бетон / Котлован / Курилка.
- Зоны в админке рисуются на схеме.
- QR одноразовый: показывает контролёр, телефон сканирует.

- Метрика зон: **посещения** (заходы в зону). Пусто = 0, мало — больше нуля, но меньше остальных (порог «мало/много» в доке, когда скажете число).
- Имитация: кнопки на телефоне Бетон / Котлован / Курилка.
- Границы зон: админ **рисует** на схеме (три фото из пакета).
- QR **одноразовый** на попытку.
