# Кейс 1. «Проходная»: контроль и учёт людей на стройке

Источник: `Кейс_1_Проходная_v2_КОТИК_на_ТРОНЕ.docx`. Формат: 3–5 человек, 7–10 часов, вайб-кодинг приветствуется. Технологии команда выбирает сама.

Документы соискателей **сняты**. Этот файл — рабочий бриф.

## Боль заказчика

Бумажный табель на входе. Отмечаются за товарища. Неизвестно, сколько людей на объекте (пожар, эвакуация). Неясно, где проводят смену. Споры по оплате вручную. Нет ответа на «что было вчера».

**Главное требование:** пройти за другого должно быть невозможно. Это гарантирует **сервер**, не честность вахтёра. Судьи будут ломать именно это. Проверка лица — сравнение «человек перед камерой» с эталоном, не «есть ли на кадре лицо».

## Роли

| Роль | Устройство | Задача |
| --- | --- | --- |
| Рабочий | телефон | подтверждение на входе/выходе; геолокация во время смены |
| Контролёр | планшет/ПК на проходной | инициирует проход, видит пропуск или причину отказа |
| Администратор | компьютер | заводит людей, эталон лица, журнал попыток |
| Руководитель | компьютер | кто внутри, аналитика зон, вопросы обычным языком |

Админ и руководитель можно совместить в одном UI, обе задачи обязательны. Нативные приложения не нужны — браузер с камерой и геолокацией.

## Обязательный объём

1. Проходная: вход/выход, лицо с камеры, подтверждение с телефона, результат и причина.
2. Телефон: одноразово получить средство подтверждения и предъявлять его; слать координаты, пока смена открыта.
3. Сервер: подлинность прохода, нельзя пройти за другого, смены, история перемещений, журнал попыток.
4. Админка: эталон лица с проверкой пригодности (нет человека / несколько людей — нельзя сохранить), список и статусы, журнал.
5. Кто сейчас внутри и с какого времени.
6. Аналитика зон: схема площадки, тепло, пусто ≠ мало, маршруты, фильтры. Зоны и привязка координат — через UI, не правкой кода. Метрика одна и описана.
7. Помощник: ответы и сводки только из данных системы. Нет данных — так и сказать. Цифры считает система, модель формулирует.

Подтверждение с телефона нельзя переслать, скопировать, сфотографировать и использовать позже.

## Что обязательно во всех кейсах

- Отдельный бэкенд. Решение «пропустить / нет» только на сервере.
- Постоянное хранилище, не память процесса и не файл рядом с кодом.
- Журнал: кто, когда, что, почему отказ.
- Модель обязательна: один изолированный слой, провайдер из конфига, **два** провайдера (внешний + рабочий локальный), инструкция как поднять локально, шаблоны промптов в репо. На хакатоне внешний сервис можно (GigaChat или другой). Смена провайдера на защите.
- Git: репо с начала, ≥15 понятных коммитов, коммиты от каждого, без секретов.
- Документы отдельными файлами: запуск, схема, журнал решений (3–6), переход на локальную модель, ограничения, отчёт об ИИ.
- На защите: судья заводит своего человека (Д9), пытается пройти за другого (Д10), просит правку 10–15 мин, спрашивает любой файл.

## Снимают с конкурса

Клиент решает проход; «есть лицо» вместо 1:1; статичный токен; данные только в памяти; рисованная аналитика; выдуманные цифры помощника; нет реального вызова модели; секреты в git; команда не может объяснить код.

## Допуск Д1–Д11 и баллы

Допуск: стенд по инструкции, сервер решает проход, три фронта, персист, модель + два провайдера, git/доки, проход судьи, нельзя за другого, владение кодом.

Качество 100: проход 28, смены/гео 10, аналитика 12, модель 15, фронт 20, культура 10, владение 5. Сценарии С1–С22 в этом файле не расписаны — только ссылки.

Не требуют: натив, свои CV-модели, реальную стройку (имитация гео ок), промышленную отказоустойчивость, интеграции, красоту ради красоты.
