# Проход: решает только сервер

28 баллов и дисквал завязаны сюда. Клиент (планшет, телефон) **показывает** результат. Решение `allow | deny` считает бэкенд после всех проверок.

Контракт попытки: [references/attempt-contract.md](references/attempt-contract.md).

## Когда вызывать

- Любой код входа/выхода, попытки, журнала.
- «Планшет сам рисует зелёный».
- Д10: пройти за другого.
- Споры про QR, TTL, повтор пакета.

## Поток (не упрощать)

```
контролёр выбирает человека + вход/выход
    → POST /attempts  { person_id, direction } 
    → сервер: attempt_id, nonce, expires_at (~20–30 с)
планшет шлёт кадр лица, привязанный к attempt_id
телефон шлёт proof (не картинку QR как единственный секрет) на тот же attempt_id
    → POST /attempts/:id/decide
    → сервер проверяет ВСЁ, пишет journal, открывает/закрывает смену
планшет показывает allow/deny + reason_human
```

Ни один шаг на клиенте не ставит человека «внутри».

## Что сервер проверяет атомарно

Все пункты обязательны. Любой провал → `deny` + код + фраза для вахтёра.

1. `attempt` существует, не истёк, статус `pending`, не `decided`.
2. `direction` согласован: вход — человека нет на объекте; выход — есть открытая смена.
3. Proof телефона: выдан этому `person_id`, этому `attempt_id`, одноразовый, подпись/сессия валидны, не replay (`jti` уже в БД → deny). См. `/phone-proof`.
4. Лицо: эмбеддинг кадра **1:1** с эталоном именно этого `person_id`. «На кадре есть лицо» ≠ проход. См. `/face-enroll-match`.
5. Нельзя собрать проход из лица А и телефона Б: оба фактора привязаны к одному `person_id`.
6. Повтор того же кадра/proof после `decided` — deny `REPLAY`.

Транзакция: решение + журнал + смена в одном commit БД. Иначе двойной вход.

## Anti-replay

- `nonce` / `jti` одноразовые, хранить использованные (TTL можно чистить, но в окне попытки — строго).
- Короткий `expires_at` на попытку (20–30 с). Протухло → `EXPIRED`, новая попытка.
- Идемпотентность `decide`: второй вызов с тем же телом не «пропускает ещё раз».
- Не принимать proof без `attempt_id`.
- Не принимать статичный токен устройства как достаточный фактор без challenge.

## Журнал (допуск)

Каждая попытка, успех и отказ:

| Поле | Зачем |
| --- | --- |
| `at` | когда |
| `person_id` / ФИО | кого заявляли |
| `direction` | вход/выход |
| `decision` | allow/deny |
| `reason_code` | стабильный enum |
| `reason_human` | русская фраза на планшет |
| `actor` | контролёр / система |
| `factors` | face score, proof ok/fail (без сырого биометрического блоба в логах UI) |

Судья спросит любой файл и «почему отказали».

## Коды отказа (не выдумывать синонимы)

`NO_SUCH_PERSON` `EXPIRED` `ALREADY_INSIDE` `NOT_INSIDE` `PROOF_MISSING` `PROOF_REPLAY` `PROOF_FOREIGN` `FACE_NO_MATCH` `FACE_QUALITY` `FACE_NOT_ENROLLED` `MIXED_IDENTITY` `REPLAY` `SERVER_ERROR`

`MIXED_IDENTITY` — лицо сошлось с эталоном А, proof от сессии Б (или наоборот). Это и есть «за другого».

## Анти-паттерны

- `localStorage.allowed = true` / WebSocket с клиента «человек вошёл».
- Зелёная кнопка контролёра без сервера (ручной override — только если бриф явно даст и всё равно в журнал).
- Один JWT на весь день как пропуск.
- Сравнивать лицо с **всеми** эталонами (1:N) и подменять выбранного человека.
- Молча пропускать, если камера не ответила.

## Первое действие

Описать `POST /attempts` и `POST /attempts/:id/decide` по контракту. Тест: два человека в БД, proof+лицо Б на попытке А → `deny MIXED_IDENTITY` / `FACE_NO_MATCH` / `PROOF_FOREIGN`. UI ещё можно заглушкой.
